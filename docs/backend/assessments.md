# Assessments API

Assessments are immutable historical health snapshots. An ASHA worker creates a draft for a patient in their own scope. The mobile application generates and uploads disease predictions, after which completion validates the feature sets and locks the assessment against further edits.

All endpoints require `Authorization: Bearer <access-token>` and an active account. Responses use the common `{ success, message, data }` envelope.

## Endpoints

| Method | Endpoint                                        | Roles                   | Purpose                                          |
| ------ | ----------------------------------------------- | ----------------------- | ------------------------------------------------ |
| POST   | `/api/v1/assessments`                           | ASHA                    | Create a draft assessment                        |
| GET    | `/api/v1/assessments`                           | PHC admin, doctor       | List assessments in the caller's permitted scope |
| GET    | `/api/v1/assessments/:assessmentId`             | ASHA, doctor, PHC admin | Get an authorized assessment                     |
| PATCH  | `/api/v1/assessments/:assessmentId`             | ASHA                    | Update an owned draft                            |
| POST   | `/api/v1/assessments/:assessmentId/complete`    | ASHA                    | Verify predictions and finalize a draft          |
| GET    | `/api/v1/assessments/:assessmentId/predictions` | ASHA, doctor, PHC admin | Get stored prediction results                    |
| GET    | `/api/v1/assessments/:assessmentId/documents`   | ASHA, doctor, PHC admin | Get documents linked to the assessment           |
| GET    | `/api/v1/patients/:patientId/assessments`       | ASHA, doctor, PHC admin | Get patient assessment history                   |

The equivalent ASHA aliases are available below `/api/v1/asha/me`, including list, create, detail, update, complete, patient history, and predictions.

## Create assessment

`POST /api/v1/assessments`

The optional `id` is a UUID generated by the mobile client. Repeating the same owned `id` is idempotent and does not create another assessment. `patientId` must identify a patient registered to the authenticated ASHA worker.

Successful creation returns a draft assessment. Upload its three mobile predictions through the predictions API, then call the completion endpoint. Missing clinical features return `422 INCOMPLETE_ASSESSMENT`; missing disease predictions return `422 INCOMPLETE_PREDICTIONS`.

## List filters

`GET /api/v1/assessments` accepts `patientId`, `ashaId`, `villageId`, `riskLevel`, `disease`, `from`, `to`, `page`, and `limit`. PHC admins are restricted to villages in their PHC. Doctors only see patients connected through their appointments or referral assignments. ASHA workers use `/asha/me/assessments` and only see their own records.

## Lifecycle and errors

- `DRAFT`: can be corrected by its owning ASHA worker.
- `COMPLETED`: all three mobile predictions exist and ordinary updates return `409 ASSESSMENT_NOT_EDITABLE`.
- Unauthorized resources are returned as not found where revealing their existence would leak patient information.
- An assessment is not marked completed until diabetes, heart-disease, and hypertension predictions have been synchronized.
